## 补步
       首先需要明确游戏中的一帧并不是一个固定值，帧的长度取决于CPU计算、画面渲染等很多因素。
       在制作游戏时比如我要求一帧执行一个逻辑步，但是实际情况中可能由于种种情况导致一帧的时间跨度足以容纳多个我要求的帧，这时我就需要在一个现实帧中执行多个逻辑步，但是执行逻辑步进行CPU计算又会占用更多时间，导致这一帧的占用时间可能进一步延长，导致现实帧的占用时间越来越长，看起来像死机了一样。
       补步简单来说就是当我发现这一帧的长度实际上需要执行多个逻辑步时补上多出来的哪些逻辑步。
       但是从上面的叙述不难看出，如果不限制补步大概率导致恶性循环，所以我们会限制单帧最大逻辑步数来防止恶性循环的发生。超出的那些帧的时间直接舍弃，这样虽然会让逻辑时间稍微落后于现实时间，但是会让游戏体验更加舒适。
       比如预设60帧执行60个逻辑步，但是我预设每一帧最大执行5步，这样轻微卡顿时可以通过最大逻辑步补救，但是过于卡顿时就可以通过最大逻辑步直接舍弃部分该帧中的时间来保证不会继续计算逻辑步进入恶性循环。

### DS说
---
> -  游戏一帧的长度不固定，取决于 CPU 计算、画面渲染等因素。固定逻辑步的目标是每秒固定执行 60 个逻辑步，与渲染帧率无关；一帧可能执行 0 步、1 步或多步。如果某一帧真实耗时较长，累积时间够多个逻辑步，就在这一帧的 Update 里连续执行多个逻辑步，这就是补步。
> -  但补步要耗 CPU，可能让这一帧更长，下一帧累积更多，形成“越补越卡”的恶性循环。所以限制单帧最大逻辑步数：单帧最多消费 maxStepsPerFrame × 固定步长 的累积时间，超出的累积时间直接丢弃并警告。这样轻微卡顿能在这一帧补上，严重卡顿会丢掉超出上限的时间，逻辑时间暂时落后于现实时间，但不会卡死。
> -  补步每帧独立判断：轻微卡顿在这一帧补完，不留下未处理时间；严重卡顿超出的累积时间当场丢弃，不会攒到后续帧。

## Awake VS 类中初始化字段
1. 从语义上来说，Awake表示在运行时初始化，而类中的初始化字段表示在实例化时初始化，对于游戏逻辑来说显然Awake更加适合用来设置初始值。
2. 从unity的机制上来说，Awake可以保证每次游戏运行时Awake中的字段都能按照要求进行初始化，而类中的初始化很可能被Inspector中的设置初始化而不是按照类的设置初始化。Inspector 覆盖只对 public/[SerializeField]
3. Domain Reload 关闭时字段初值不重跑

## 控制台调试输出
       如果要使用控制台调试输出，应该用Debug，而不是Console，后者会直接将信息加入标准信息流，不能在unity中查看
       另外，正常输出用成员函数Log,警告输出未LogWarning，红字错误用LogError,如果要输出数字($"context{num}")也可以用("context1" + num + "context2")输出
